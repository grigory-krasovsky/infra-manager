# Ранбук: настройка infra-manager

Всё, что нельзя сделать кодом — ручные шаги в чужих системах. Каждый шаг заканчивается
значением, которое надо положить в `.env`.

## 0. Локальный запуск

```powershell
Copy-Item .env.example .env    # затем заполнить POSTGRES_PASSWORD
.\scripts\up.ps1
```

Проверка: `curl http://localhost:8080/actuator/health` → `{"status":"UP"}`.

### Почему скрипт, а не `docker compose up -d --build`

Команда внутри та же, плюс уборка двух видов мусора, который иначе копится от
запуска к запуску. Аргументы пробрасываются в compose как есть, на Linux-сервере
то же самое делает `scripts/up.sh`.

**Недосозданные контейнеры.** Прерванный `up` — Ctrl+C, закрытое окно, упавшая
обёртка — застаёт compose посреди замены контейнера: прежний уже переименован в
`<hash>_infra-manager-app-1`, новый создан, но не запущен. Следующий запуск
спотыкается об занятое имя:

```
Error response from daemon: Error when allocating new name: Conflict.
The container name "/infra-manager-app-1" is already in use by container ...
```

Скрипт перед `up` удаляет контейнеры проекта в состоянии `created` — в нём
бывают только такие обрубки, намеренно остановленный контейнер имеет `exited`.

**Безымянные образы.** Каждая пересборка снимает тег с предыдущего образа
приложения, и тот остаётся как `<none>` насовсем — за сутки правок набирается два
десятка. Скрипт после `up` делает `docker image prune` с фильтром по метке
`org.opencontainers.image.title=infra-manager` (ставится в `Dockerfile`), поэтому
трогает только образы этого проекта, а не чужие на той же машине.

Освобождённое место при этом покажут нулевым: слои у образа общие с кэшем
сборки, и отдаст их именно кэш — но только после того, как образ удалён.

Если мусор уже накопился, разово:

```powershell
docker image prune -f                         # все безымянные образы на машине
docker builder prune -f --filter until=168h   # кэш сборки, не использованный неделю
```

### После правки `.env` — обязательно `--force-recreate`

```powershell
.\scripts\up.ps1 --force-recreate app
```

Переменные окружения фиксируются в момент создания контейнера, и `docker compose
up -d` изменение содержимого `env_file` не замечает — контейнер продолжает жить
со старыми значениями. Симптом коварный: в файле новый токен, а сервис ходит со
старым и получает 401. Проверить, что видит контейнер:

```powershell
docker compose exec app printenv BAMBOO_TOKEN
```

Порт Postgres на хосте — `5433` (не 5432), чтобы не конфликтовать с локально
установленной базой. Меняется через `DB_HOST_PORT`.

## 1. Telegram-бот

*Нужен для: уведомлений о деплое (фаза 2–3).*

1. Написать [@BotFather](https://t.me/BotFather) → `/newbot`, задать имя и username.
2. Забрать токен вида `123456789:AA...` → `TELEGRAM_BOT_TOKEN`, и поставить
   `TELEGRAM_ENABLED=true`.
3. Добавить бота в нужный чат/канал. Для канала — сделать администратором,
   иначе он не сможет писать.
4. Узнать `chat_id`: отправить в чат любое сообщение и открыть
   `https://api.telegram.org/bot<TOKEN>/getUpdates` — `chat_id` группы отрицательный
   (супергруппы начинаются с `-100`). Он идёт в конфиг, не в `.env`:

```yaml
infra-manager:
  telegram:
    routes:
      - chat-id: "-1001234567890"
        environments: [STAGE, PROD]   # пусто или отсутствует = все стенды
```

Уведомления отправляются наружу, входящий порт не нужен.

Пока `TELEGRAM_ENABLED=false`, уведомления всё равно кладутся в `outbound_task`
и помечаются `SKIPPED` — то есть пропажа видна в таблице, а не теряется молча.

### Если `api.telegram.org` недоступен напрямую

Выглядит это как `I/O error on POST` в `last_error` у задач `TELEGRAM`, которые
досрочно кончились статусом `FAILED`. Лечится прокси — **только для Telegram**:

```dotenv
TELEGRAM_PROXY_TYPE=socks5          # http | socks5
TELEGRAM_PROXY_HOST=host.docker.internal
TELEGRAM_PROXY_PORT=1080
TELEGRAM_PROXY_USERNAME=            # только для http; для socks5 оставить пустым
TELEGRAM_PROXY_PASSWORD=
```

Общесистемные `https.proxyHost` и `HTTPS_PROXY` для этого не годятся принципиально:
они увели бы в тот же прокси обращения к Bitbucket и Bamboo, а те живут в сети
`192.168.0.x`, куда через внешний прокси хода нет. Поэтому прокси настраивается
у клиента Telegram, а остальные интеграции его не видят.

Три вещи, о которые тут спотыкаются:

- **`host.docker.internal`, а не `localhost`.** Прокси обычно запущен на самой
  машине, а `localhost` внутри контейнера — это сам контейнер.
- **Тип обязателен и не угадывается.** HTTP-прокси получает CONNECT-запрос, SOCKS
  работает уровнем ниже. От типа зависит и клиент: `java.net.http.HttpClient` не
  умеет SOCKS вовсе, поэтому под `socks5` берётся фабрика поверх
  `HttpURLConnection`. Указан не тот тип — соединение просто не установится.
- **MTProto-прокси не подойдёт.** Ссылка вида `tg://proxy?server=…&secret=…` — это
  транспорт клиентского протокола Telegram, он умеет говорить только с его
  дата-центрами. Мы же ходим в Bot API обычным HTTPS, и MTProto его не пропустит.
  Годятся только HTTP и SOCKS5 — те, у которых есть просто адрес и порт.

Проверить маршрут до всякой отправки, прямо с хоста:

```bash
curl -x socks5h://HOST:PORT "https://api.telegram.org/bot<TOKEN>/getMe"   # socks5
curl -x http://HOST:PORT    "https://api.telegram.org/bot<TOKEN>/getMe"   # http
```

`{"ok":true,...}` означает, что прокси до Telegram доходит.

Задачи, которые уже кончились `FAILED`, сами не оживут — попытки исчерпаны.
Вернуть их в очередь после того, как прокси заработал:

```sql
UPDATE outbound_task SET status = 'PENDING', attempts = 0, next_attempt_at = now()
WHERE target = 'TELEGRAM' AND status = 'FAILED';
```

## 2. Trello

*Нужен для: карточек PR (фаза 4).*

Ключ API с 2024 выдаётся только через Power-Up — просто «сгенерировать ключ» больше нельзя.

1. Открыть <https://trello.com/apps/admin>, создать Power-Up (workspace — тот, где
   лежит доска; остальные поля можно заполнить формально).
2. В созданном Power-Up вкладка **API Key** → *Generate a new API Key* → `TRELLO_KEY`.
   Ключ не секрет.
3. Там же по ссылке **Token** пройти авторизацию → `TRELLO_TOKEN`. **Это секрет**,
   даёт доступ к данным аккаунта.
4. ID доски: открыть доску и добавить `.json` к URL, либо взять из
   `https://api.trello.com/1/members/me/boards?key=<KEY>&token=<TOKEN>`.
5. Поставить `TRELLO_ENABLED=true` и описать соответствие репозиториев доскам:

```yaml
infra-manager:
  lifecycle:
    repos:
      - project-key: INFRA
        repo-slug: backend
        trello-board-id: "5f2b..."
```

Колонки должны существовать на доске — имена сверяются без учёта регистра, но
отсутствующее имя роняет задачу с явной ошибкой, а не молча оставляет карточку
на месте.

**Метки.** На карточку вешаются две: проект (`prefix` репозитория — LIZA,
LIZA-API, ЦСВ) и целевая ветка. Проект дублирует префикс в заголовке намеренно:
по заголовку доску не отфильтруешь, а репозитории делят одну доску. Недостающие
метки создаются на доске сами.

Цвет метки задаётся в `trello.label-colors` и не только назначается при создании,
но и восстанавливается, если на доске он оказался другим — иначе метка, заведённая
до настройки, осталась бы прежнего цвета навсегда. Метке, которой в списке нет,
достаётся первый свободный на доске цвет, чтобы две плашки не совпали. Палитра
Trello: `green`, `yellow`, `orange`, `red`, `purple`, `blue`, `sky`, `lime`,
`pink`, `black`; любое другое значение не даст приложению стартовать.

```yaml
infra-manager:
  trello:
    label-colors:
      - label: prod
        color: red
      - label: test
        color: green
```

Где имя ветки расходится со смыслом, метку можно переименовать:

```yaml
infra-manager:
  lifecycle:
    branch-labels:
      # PR в postgres — это по смыслу PR в тест.
      - branch: postgres
        label: test
```

Подменяется только метка: в заголовке и описании карточки ветка называется
своим именем.

**Фон карточки.** Обложка (cover) — цветной фон, видный прямо на доске, в отличие
от метки, которая на лицевой стороне карточки всего лишь плашка. Цвет задаётся
репозиторию: что происходит с пул-реквестом, и так говорит колонка, а вот чей это
репозиторий, на общей доске иначе видно только по метке.

```yaml
infra-manager:
  trello:
    # normal — полоса над заголовком, full — заливка всей карточки.
    cover-size: normal
  lifecycle:
    repos:
      - project-key: LIZA
        repo-slug: liza
        prefix: LIZA
        trello-board-id: "6aa2..."
        cover: blue
```

Палитра та же, что у меток; незнакомый цвет не даст приложению стартовать.
Репозиторий без `cover` оставляет свои карточки без фона — и именно снимает его,
а не оставляет как есть: убранный из конфигурации цвет уходит и с уже покрашенных
карточек при первом же событии по их пул-реквесту. Сверка и суточный проход
обложку не трогают вовсе.

Размер общий для всех: размером здесь ничего не сказано, а разные размеры у
соседних карточек читаются как сбой. Карточке, которую только что создали, фон
доезжает вторым запросом — `POST /1/cards` параметра `cover` не принимает, его
понимает только `PUT`.

**Кого назначать исполнителем карточки.** Общего идентификатора у Bitbucket и
Trello нет: на доску людей приглашают по личным почтам, а корпоративный адрес с
ними не связан — и чужие адреса Trello через API всё равно не отдаёт. Поэтому
автор ищется по имени: «Красовский Григорий Игоревич» из Bitbucket находит
«Grigory Krasovsky» в Trello. Порядок слов, отчество, латиница против кириллицы
и расхожие варианты записи (`Mihail`/`Mikhail`, `Kuznecov`/`Kuznetsov`,
`Grigory`/`Grigoriy`) значения не имеют; уменьшительные («Гриша») — имеют.

Отсюда единственное требование к участнику доски: **в профиле Trello должно
стоять настоящее имя**. Приглашая человека, попросите его это проверить.

Когда имя не годится — стоит псевдоним или под него подошло сразу несколько
участников (тогда не назначается никто), — человек прописывается явно:

```yaml
infra-manager:
  trello:
    members:
      # Слева логин или отображаемое имя из Bitbucket, справа id участника,
      # его username или полное имя. Логин с точкой — в скобках, иначе Spring
      # разберёт его как вложенные ключи.
      "[g.krasovsky]": 5f2a9c1b7d4e3f0012ab34cd
```

Ростер доски со всеми тремя написаниями:

```bash
curl -s "https://api.trello.com/1/boards/<BOARD>/members?key=<KEY>&token=<TOKEN>&fields=id,username,fullName"
```

Ненайденный автор — не ошибка: карточка просто остаётся без исполнителя, имя
автора в описании есть в любом случае. Но в лог это пишется (`WARN ... matches`,
однократно за 10 минут жизни кэша) — там же видно и неоднозначность, и мёртвую
запись в `members`.

Ограничения бесплатного тарифа, которые нас касаются: 10 досок на workspace,
карточки не ограничены. Лимит частоты API — сотни запросов на 10 секунд на ключ;
исходящий воркер это соблюдает и обрабатывает `429`.

**Вебхуки Trello не используем.** Trello проверяет `callbackURL` HEAD-запросом и
должен сам до него достучаться — до машины во внутренней сети он не дотянется.
Обратное направление читаем опросом: `TRELLO_RECONCILIATION_ENABLED=true`
включает периодическую сверку, которая замечает карточки, перетащенные или
удалённые руками. По умолчанию она только пишет в лог; `on-drift: restore`
возвращает карточку на место, `on-missing: forget` забывает удалённую карточку,
чтобы следующее событие по этому PR создало новую.

**Отметка о выполнении.** `TRELLO_COMPLETION_ENABLED=true` включает суточный
проход, который отмечает выполненной карточку пул-реквеста, закрытого неделю
назад и раньше. Влит он или отклонён — неважно: и там и там решение принято, и
отметка говорит не «сделано хорошо», а «здесь всё закончено».

```yaml
infra-manager:
  trello:
    completion:
      interval: 24h
      after: 7d
```

Карточка при этом остаётся в своей колонке — колонка отвечает на вопрос «чем
кончилось», и от того, что прошла неделя, ответ не меняется.

**Неделя считается от закрытия пул-реквеста в Bitbucket** (`closedDate`, при его
отсутствии — `updatedDate`; в базе это `pr_card_link.closed_at`), а не от того,
когда карточка переехала в колонку. Разница не теоретическая: в колонку карточка
попадает позже — на время простоя сервиса, а перетащенная руками и на сколько
угодно, — и отсчёт от доски растягивал бы неделю на ровном месте.

Колонка всё же проверяется: карточка должна лежать в одной из **конечных** —
тех, куда её кладут `pr:merged` и `pr:declined`. Увезли из них — на доске она
больше не о законченной работе, что бы ни говорил Bitbucket. Отдельной настройки
для этих колонок нет намеренно: две настройки с одним смыслом однажды разойдутся.

Вместе с отметкой карточке проставляется **срок**, равный моменту закрытия. Это
не украшение: отметку без срока Trello принимает, но не показывает ни на
карточке, ни на доске. Отсюда же следствие — срок, выставленный на такой карточке
руками, будет перезаписан.

Чего проход **не делает**: переоткрытый пул-реквест отметку не снимает. Карточка
уедет обратно в ревью с зелёной галочкой, и убрать её придётся руками. Случай
редкий (переоткрывают отклонённое), а снимать отметку пришлось бы в другом
месте — там, где карточка переезжает по событию.

Карточкам, заведённым до появления столбца `closed_at`, миграция проставила время
последнего обновления: по закрытому пул-реквесту событий больше не приходит, и
переспросить момент закрытия не у кого. Поэтому первый проход отметит разом всё,
что закрыто давно. У ещё открытых пул-реквестов эта приблизительная дата
перезапишется настоящей, как только придёт событие о закрытии.

## 3. Bitbucket Data Center

*Нужен для: событий PR (фаза 4).*

1. **HTTP access token** (для чтения PR через REST): профиль → *Manage account* →
   *HTTP access tokens* → создать с правами `Project read` / `Repository read`
   → `BITBUCKET_TOKEN`.
2. **Вебхук** на каждом нужном репозитории: *Repository settings* → *Webhooks* → *Create webhook*.
   - URL: `http://<хост-с-infra-manager>:8080/webhooks/bitbucket`
   - Secret: длинная случайная строка → одновременно в `BITBUCKET_WEBHOOK_SECRET`
   - События: `Pull request` → opened, modified, source branch updated, approved,
     unapproved, changes requested, merged, declined, deleted
3. Поставить `BITBUCKET_ENABLED=true` — без этого эндпоинт не поднимается.
4. Кнопка *Test connection* должна вернуть 200.

**Вебхук требует, чтобы Bitbucket смог открыть соединение к нам.** Из-за пределов
корпоративной сети — работа из дома, VPN, RDP — он этого не сможет, и никакие
права администратора не помогут. Тогда вместо вебхука включается опрос.

### Опрос PR вместо вебхуков

```
BITBUCKET_POLL_ENABLED=true
BITBUCKET_TOKEN=<HTTP access token, прав Repository read достаточно>
BITBUCKET_BASE_URL=https://bitbucket.example.com
```

Опрашиваются только репозитории из `infra-manager.lifecycle.repos` — события от
репозитория, который мы не зеркалим, некому обрабатывать.

Вебхук сообщает, *что произошло*; опрос видит только *как сейчас*, поэтому
событие восстанавливается сравнением с прошлым снимком (таблица `pr_poll_state`):
смена состояния, новый головной коммит, изменение набора апрувов, инкремент
`version`. На выходе получается payload той же формы, что шлёт вебхук, поэтому
дальше работает та же цепочка.

Первый проход выдаёт `pr:opened` только для **открытых** PR — закрытые просто
записываются, иначе доска мгновенно заполнилась бы историей за годы.

**Удаление PR опрос ловит отдельной сверкой.** Сравнивать тут не с чем: удалённый
пул-реквест из списка просто исчезает, и без сверки `pr:deleted` на этом пути не
поднимался бы никогда, а его карточка оставалась бы на доске живой. Заведённый
заново из той же ветки PR получает новый номер и, значит, новую карточку — так
доска и двоится.

Поэтому после каждого прохода снимки в состоянии `OPEN` сверяются со списком, и о
каждом, кого в списке нет, Bitbucket спрашивается отдельным запросом: со страницы
PR пропадает и просто от возраста (`max-results`), а принять это за удаление —
значит убрать с доски карточку живого PR. Удалённым он считается только по ответу
`404`; любая другая ошибка означает «не знаем», и следующий проход спросит снова.
Найденный помечается в `pr_poll_state.state = DELETED` — это состояние не от
Bitbucket, а наше: без него о покойнике спрашивали бы каждые две минуты вечно.
Закрытые PR не проверяются: их карточки уже в конечной колонке, а со страницы они
уходят пачками.

Карточка при этом уезжает в архив **как есть** — заголовок, описание, метки и
чек-лист не трогаются. У удалённого PR содержимого больше нет, и переписать
карточку тем немногим, что осталось, значило бы стереть с неё всё полезное ровно
перед тем, как убрать с доски.

**Если карточки понадобилось пересоздать** (например, доска в Trello появилась
уже после включения опроса), очистите снимки — следующий проход снова увидит все
открытые PR как новые:

```powershell
docker compose exec db psql -U inframanager -d inframanager -c "TRUNCATE pr_poll_state"
```

Bitbucket подписывает тело запроса заголовком `X-Hub-Signature: sha256=<hmac>`,
ключ события кладёт в `X-Event-Key`. Сервис проверяет подпись по сырым байтам тела
и отвечает `401` на несовпадение.

### Жизненный цикл карточки

Событие → колонка задаётся списком пар, а не словарём. Причина техническая:
двоеточие недопустимо в имени property, и словарь пришлось бы писать как
`"[pr:opened]": Review` — выглядит опечаткой, а если «поправить», молча
перестанет работать.

```yaml
infra-manager:
  lifecycle:
    event-to-list:
      - event: "pr:opened"
        list: Review
      - event: "pr:merged"
        list: Merged
    reopen-on-new-commits: true
```

События, которых нет в списке, обновляют заголовок и описание карточки, но не
двигают её — именно так и должен вести себя `pr:modified`. `pr:deleted`
архивирует карточку. При `reopen-on-new-commits` новые коммиты возвращают
карточку в колонку `pr:opened`.

**Колонку двигает только вердикт ревьюера — и только о том коде, который в ветке
сейчас.** `NEEDS_WORK` → «Запрошены изменения», апрув → «Аппрув», всё остальное —
«Ревью». Комментарии и незакрытые задачи в Bitbucket статус не меняют, и мы их
намеренно не читаем: колонка отвечает на вопрос «чей ход», а промежуточные
состояния внутри ревью — ответственность ревьюера, а не доски.

Из этого следует одно поведение, которое выглядит неожиданным, но задумано
именно так: пуш автора возвращает карточку в «Ревью» даже после `NEEDS_WORK` —
считается, что автор починил обсуждённое и мяч снова у ревьюера.

Свежесть вердикта берётся из `lastReviewedCommit` — это коммит, на котором
ревьюер нажал «Approve» или «Needs work». Само по себе это поле за веткой не
следует, и сравнение с её головой отвечает, о нынешнем ли коде вердикт. Без него
статуса не хватало: повторное «нужны правки» статус не меняет — он и так
`NEEDS_WORK`, — так что второй заход ревьюера ничем не отличался от первого, и
карточка оставалась в «Ревью», пока ход был у автора. По той же причине апрув,
пришедший в одном проходе опроса с пушем, больше не проигрывает ему молча:
одобрена нынешняя голова ветки или нет, видно прямо.

**Задачи ревью попадают на карточку чек-листом «Задачи ревью».** Пункт на задачу,
галочка — закрытая задача, и неважно, кто её закрыл. Колонку они не двигают:
чек-лист отвечает на вопрос «что просили поправить», а не «чей ход».

Чтобы список не устаревал, опрос отдельно считает отпечаток задач и при его
изменении поднимает `pr:modified` — событие, не отображённое ни на какую
колонку, поэтому карточка обновляется на месте. Отпечаток лежит в
`pr_poll_state.task_digest`; без него изменение осталось бы незамеченным, ведь
задачу открывают и закрывают, не трогая ни версию пул-реквеста, ни ветку, ни
статусы ревьюеров. Стоит это одного запроса на открытый пул-реквест за проход;
у закрытых задачи не спрашиваются.

Чужие чек-листы на карточке не трогаются — только свой, названный «Задачи
ревью». Если Bitbucket недоступен, чек-лист остаётся прежним: «не знаем» и
«задач нет» — разные вещи, и стирать замечания из-за сетевой заминки нельзя.

**Пул-реквест, который не влить из-за конфликтов, получает `⚠️` в начале
заголовка карточки** — «⚠️ ЦСВ · [ORVD-1047] Копирование бизнес-процесса».
Значок снимается сам, как только конфликт разошёлся или пул-реквест закрыли.

Колонку конфликт не двигает и меткой не становится намеренно: колонка отвечает
на вопрос «чей ход», метки — «что это за карточка», и оба ответа от конфликта не
меняются. Одобренный пул-реквест с конфликтом так и остаётся в «Аппрув» —
с предупреждением в заголовке.

Факт берётся из результата пробного мержа, который Bitbucket кладёт прямо в
список пул-реквестов (`properties.mergeResult`), так что обычно он бесплатен.
Считает Bitbucket мерж лениво: пока пул-реквест никто не открывал, там стоит
`current: false` и ответ относится к старым головам веток. На такие
пул-реквесты делается отдельный запрос `GET …/pull-requests/{id}/merge` — он и
отвечает точно, и заставляет Bitbucket мерж пересчитать, после чего в списке
снова появляется свежий ответ.

Смену отслеживает `pr_poll_state.conflicted`, и при ней поднимается
`pr:modified`. Без этой колонки конфликт остался бы незамеченным вовсе:
появляется он от чужого мержа в целевую ветку, а в самом пул-реквесте при этом
не меняется ни версия, ни ветка, ни статусы ревьюеров. Если ответа получить не
удалось, остаётся прошлый: выдуманное «конфликтов нет» сняло бы предупреждение
с карточки на первой же заминке Bitbucket.

Прочие причины, по которым мерж запрещён, — недобор аппрувов, незакрытые
задачи, выставленный `NEEDS_WORK` — значком не отмечаются: их доска уже
показывает колонкой и чек-листом.

На пути с вебхуками предупреждения не будет: результата пробного мержа в теле
вебхука нет, а «не знаем» — не повод пугать.

## 4. Bamboo Data Center

*Нужен для: уведомлений о деплое (фаза 3).*

Сначала проверить, что в этой версии есть вебхуки: **Administration → Communication →
Webhook templates**. Если раздела нет — переключиться на опрос:
`infra-manager.bamboo.source=poll`.

Если раздел есть — `BAMBOO_SOURCE=webhook`:

1. Создать webhook template. Тело задаём мы сами — готовый JSON лежит в
   `docs/bamboo-webhook-template.json`.
2. В шаблон добавить заголовок `X-Infra-Manager-Secret` с общим секретом
   → `BAMBOO_WEBHOOK_SECRET`. Если версия Bamboo не даёт задавать заголовки,
   секрет принимается и как query-параметр `?secret=...` — но он попадёт
   в логи доступа, так что заголовок предпочтительнее.
3. URL: `http://<хост-с-infra-manager>:8080/webhooks/bamboo`
4. Подключить шаблон как тип нотификации в конфигурации deployment environment
   для событий завершения деплоя.

Переменная `deploymentProjectName` есть не во всех версиях. Если в сообщениях
вместо имени проекта появляется `UNKNOWN`, задать соответствие по id:

```yaml
infra-manager:
  bamboo:
    project-names:
      "12345": INFRA
```

Если раздела нет — `BAMBOO_SOURCE=poll`, нужен `BAMBOO_TOKEN` и явный список
окружений (их id виден в URL окружения в Bamboo):

```yaml
infra-manager:
  bamboo:
    poll:
      interval: 60s
      environments:
        - id: 12345
          project-name: INFRA
          environment-name: STAGE
```

Опрос не хранит курсор: каждый проход перечитывает последние результаты, а
повторы отсекает уникальный индекс. После рестарта ничего не теряется и не
дублируется.

## 5. Jira Data Center

*Нужен для: подстановки названия задачи в заголовок карточки (фаза 5). Необязателен —
без него карточка называется по заголовку PR.*

1. Профиль → *Personal Access Tokens* → создать → `JIRA_TOKEN`.
   PAT в Data Center передаётся как `Authorization: Bearer <token>`.
2. `JIRA_BASE_URL` — адрес, видимый из контейнера, и `JIRA_ENABLED=true`.

Ключ задачи берётся из имени ветки, иначе из заголовка PR. Если в ветках
попадаются посторонние строки, похожие на ключи, шаблон можно сузить:
`infra-manager.jira.issue-key-pattern: "(INFRA-\\d+)"`.

Заголовок карточки: `[PROJ-123] Название задачи (PR #42)` при удачном обогащении,
`[PROJ-123] PR #42 · заголовок PR` если ключ известен, а Jira недоступна, и
`PR #42 · заголовок PR` если ключа нет. Номер PR остаётся в заголовке всегда:
карточка — это PR, и два PR по одной задаче не должны выглядеть одинаково.

Обогащение никогда не роняет обработку события — недоступная Jira означает
только более простой заголовок.

Вебхуки Jira не настраиваем: статусы задач жизненный цикл карточек не двигают.

## 6. Сетевая доступность

Контейнеру нужно ходить в Bamboo/Bitbucket/Jira, а Bamboo и Bitbucket — стучаться в него.

- Пока всё на локальной машине: внешние системы адресуются как
  `host.docker.internal` (в compose проброшено через `host-gateway`).
- На рабочем сервере: заменить на внутренние имена хостов в `.env`. Образ тот же,
  меняется только `.env`.
- Проверить из контейнера: `docker compose exec app wget -qO- <BASE_URL>/status`.
